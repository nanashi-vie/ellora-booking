# Customer confirmation and admin handling of disputed completion

## Scope and accepted behavior
- When an owner completes an online appointment, the customer sees two actions: confirm service was used, or report that it is not complete with a required reason.
- A negative response creates an internal admin case. The user explicitly chose admin resolution with a required conclusion and either uphold completion or return the appointment to `IN_PROGRESS`.
- Admin cases include the appointment, service/time/employee, customer contact, salon contact/address and salon-owner contact so the admin can contact both parties. Clipboard actions are local; no automatic external messages.

## Implementation plan and contract
- Preserve the existing six booking lifecycle statuses and completed revenue behavior while awaiting a response or admin resolution. Add a separate nullable confirmation state (`PENDING`, `CONFIRMED`, `DISPUTED`, `ADMIN_CONFIRMED`, `REOPENED`), completion version (default 0), response/resolution timestamps and current reason/conclusion snapshots to Booking. New owner completion increments the version and resets the response; guest walk-ins need no account confirmation.
- Add a `booking_completion_disputes` history table: booking/version unique, reason, status `OPEN`/`UPHELD`/`REOPENED`, creation/resolution time, resolving admin and conclusion. Keep histories across repeated completion cycles. Lock the booking row first for customer response and admin resolution; reject stale versions and conflicting terminal responses, make identical retries idempotent.
- Legacy completed rows with a review are treated as confirmed; rows without a review await a response. Before a legacy completed write, freeze a missing completedAt to its old updatedAt or scheduledAt and mark estimated, preserving the existing reporting bucket.
- Uphold preserves completion time. Return sets `IN_PROGRESS`, clears completedAt and retains the admin conclusion for both parties; it consequently leaves completed reports until a later owner completion. Existing recorded billing payments are not altered or refunded automatically. Future availability must remain coherent when reopening an active time interval.
- Only confirmed/admin-confirmed customers can submit a new review. Existing reviews remain intact. Customer actions are restricted to the booking's customer; admin actions and full contact data are admin-only. Resolve records use the authenticated admin identity.
- `POST /bookings/{id}/completion-response` body `{completed:boolean, reason?:string, completionVersion:number}` returns BookingResponse.
- `GET /admin/booking-disputes?status=OPEN|UPHELD|REOPENED&page=0&size=20` (omitted status means all) and `GET /admin/booking-disputes/{id}` return paginated cases and a case respectively.
- `PATCH /admin/booking-disputes/{id}/resolution` body `{outcome:'UPHELD'|'REOPENED', note:string}` returns the resolved case.
- BookingResponse adds `completionConfirmation`, `completionVersion`, `completionRespondedAt`, `completionCustomerNote`, `completionAdminNote`, `completionResolvedAt`.
- Admin case fields: `id`, `bookingId`, `completionVersion`, `status`, `reason`, `createdAt`, `resolvedAt`, `resolvedBy`, `adminNote`; `customerName`, `customerPhone`, `customerEmail`; `salonId`, `salonName`, `salonPhone`, `salonEmail`, `salonAddress`; `ownerName`, `ownerPhone`, `ownerEmail`; `serviceName`, `servicePrice`, `scheduledAt`, `durationMinutes`, `employeeName`, `bookingStatus`, `completedAt`.
- Customer UI uses the real MyBookings page, preserves reason drafts, blocks duplicate submissions, displays admin conclusions and prevents an older polling response overwriting mutations. Admin gets a guarded lazy page and shared navigation link with pending/resolved cases, contact/copy details and resolution form. Match existing Ellora styling without new dependencies.
- Add an idempotent, additive SQL script for Supabase (`ddl-auto:none`), preserving booking rows and enabling RLS on the new internal table. Apply before local backend recompilation; do not create real bookings/cases or resolve real disputes for testing.

## Touched areas and verification
- Backend: Booking/DTO/repository/service, separate dispute entity/repository/service/controller/DTOs, ReviewService, focused lifecycle/security tests and SQL.
- Frontend: Booking API model/service, customer MyBookings, new admin API/page/specs and route/navigation. Owner polling continues to use existing statuses.
- Verify positive/negative responses, duplicate/stale versions, same-owner/customer/admin permissions, case detail contact visibility, resolution history, reopen/recompletion, legacy revenue timestamps and review gating with tests. Exercise actual customer/admin template actions, clipboard failure, validation, polling races and failure draft retention.
- Run relevant backend/frontend regressions, production build and read-only local probes. Peer review and fix findings before completion. No Git push, deployment, external messaging or changes to recorded payments.

## Implemented and verified
- Added a separate completion service/controllers and dispute entity/repository/DTOs while preserving BookingService constructor compatibility. Customer responses and admin decisions persist with booking version checks, immutable history and authenticated identities. New completion resets the current response; repeated identical requests do not create duplicate cases or completion cycles.
- Full admin details include customer phone/email, salon phone/email/address, owner phone/email, appointment/service/employee/time, reason and recorded conclusion. Admin has a guarded lazy page, pending/resolved filters, pagination, clipboard actions and both resolution outcomes. After resolution the current page is refilled so removing a pending case cannot skip a case across page boundaries; refresh failures preserve the saved outcome and prevent navigation using stale offsets.
- Customer MyBookings displays confirmation/report actions, requires a reason, preserves failed drafts and shows admin conclusions. Review eligibility is enforced in UI and backend. Silent polling cannot remove an open later-page editor or overwrite a mutation, and a draft is bound to its original completion version. Reopened owner appointments show the admin's request in the active list and calendar.
- Reopening a current/future original interval checks employee conflicts while holding salon then booking locks; historical corrections retain the original appointment interval. Review creation now uses the same salon-to-booking lock order as admin resolution, including retries of upheld cases.
- Applied the additive Supabase SQL and verified the six columns, dispute table/index and RLS. Existing appointments, reviews and recorded payments were preserved. New APIs and completion DTO metadata are loaded by the running local backend.
- Verification passed: 130 backend tests, 78 frontend tests across eight selected suites, and production browser/server build. FE owner/admin pages and BE ping returned HTTP 200; unauthenticated admin case access returned HTTP 401. Peer backend and frontend review findings were fixed and approved.
- Verification used mocked business actions and read-only local probes; no real booking, case, review, resolution, email or payment was created or changed for testing. No browser surface was available for screenshot QA; real Angular templates/actions were exercised by fixture tests. Temporary test configurations were removed. Local FE/BE remain running; no Git remote or deployment changes.
