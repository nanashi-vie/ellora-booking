# Admin header navigation

## Request and bounded decision
- User identifies redundant customer links in the admin avatar menu and no clear return to the dashboard after visiting public pages through the logo. Use the existing architect/review/verify workflow with the authorized Codex substitution; this plan precedes edits.
- Root selected the smallest scope: shared Header plus focused tests/documentation. Admin avatar menu contains only **Bảng điều khiển** and **Đăng xuất**; remove customer profile/security/bookings/rewards entries for ADMIN. Existing customer security route and settings layout remain untouched and usable. No new admin security route/sidebar or backend change.
- Add a dashboard return link for admin navigation on desktop/mobile and make admin's logo destination `/admin/dashboard`. Customer logo remains `/`; retain customer navigation and fix its currently invalid mobile profile/security/booking paths to the existing `/setting/...` routes. Hide the business-registration marketing link from the admin header.

## Canonical role and loading
- Determine the role only from `ProfileApiService.getCurrentUser()` (`GET /profiles/me`), after the existing browser/auth check. Do not infer ADMIN from the current URL, Cognito name/groups, localStorage or an input controlled by public routes.
- Read the canonical profile once per logged-in Header initialization, using its fullName/email for display and the exact `role === 'ADMIN'` check. Remove the separate Cognito display-profile read if it becomes redundant. Unknown/failed profile must not show admin privileges or assume CUSTOMER; use a minimal logged-in logout fallback.
- Existing route guards already make fresh canonical profile reads. Root explicitly accepts this one additional Header GET rather than introducing a shared auth/profile cache or session state for this small UI task. Do not change ProfileApiService, guard behavior, role authorization or HTTP security.
- Preserve browser/SSR guards, avoid reads for anonymous/SSR rendering, and guard late async responses against destruction/logout so they cannot restore an admin menu after sign-out. Logout clears Header role/name state and closes menus before navigation.

## Implementation
1. Implement the canonical role/display state in the shared Header; limit profile acquisition to its normal auth initialization path.
2. Render the role-appropriate desktop/mobile avatar menu and dashboard return/logo links. Keep native links/buttons, accessible names/expanded state and existing menu/search close behavior. Keep the header's current responsive shape/palette and search behavior unless a necessary overlap fix is demonstrated.
3. Add focused Header tests for ADMIN, CUSTOMER, anonymous and unknown/profile-failure states; desktop/mobile parity and valid destinations; exactly one profile read per Header initialization; stale completion after logout/destroy; normal logout and preserved search behavior. Existing guards remain independently authoritative.
4. Run focused header/search and relevant admin/customer/guard regressions, then final production browser/server build. Root visually verifies the real shared Header in an isolated admin fixture on desktop/mobile, clicks the dashboard return/logo/menu/logout controls without changing a real account, and confirms no overflow/overlap. Remove fixtures/config and stop preview processes.
