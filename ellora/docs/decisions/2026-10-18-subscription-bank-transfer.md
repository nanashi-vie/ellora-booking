# Subscription activation after a bank transfer

## Correction and scope
- The user clarified that the salon must transfer money and admin must confirm receipt before registration becomes active. This supersedes the earlier subscription decision's approval-without-payment interpretation. Existing plan benefits, calendar-month renewal, priority/ranking, ownership and quote locking remain unchanged.
- Architect review used the current subscription service/DTO/schema and PlatformBillingService/PlatformBillingSettings. Existing bank configuration contains only `qrUrl`, managed through `POST /api/admin/billing/qr`; reuse it rather than invent bank/account details or a payment provider. No automatic bank verification, gateway, payment email/cron, percentage-fee change or Git push is included.
- Required order: choose a positive quoted plan → receive its QR/amount/unique transfer instructions → transfer externally → owner reports the transfer → admin manually checks bank receipt and explicitly confirms the exact quoted amount → activate/renew. An owner report is only a declaration, never proof of received money.
- Mandatory transfer replaces the earlier optional-zero-promotion assumption: new enabled plans and new requests require a whole-VND price **>0** within the existing 15-digit limit. Disabled catalog entries may retain null/zero. Existing zero-price approvals/periods are preserved; old zero-price pending requests cannot be paid/activated and admin can reject them. No fake amount is substituted.

## Settled API and lifecycle
- Retain the PENDING/APPROVED/REJECTED enum and one-pending-per-salon rule. Present PENDING with no report as **Chờ chuyển khoản**, and PENDING with a report as **Chờ đối soát**. Only a received-money approval changes entitlement.
- Existing `POST /api/owner/subscription/requests {tier,expectedPrice}` still creates a PENDING quote, but requires an ACTIVE salon, positive available price and a configured nonblank QR. Read and copy the current platform QR into the request snapshot; the QR upload service need not change. The returned request includes `paymentQrUrl`, deterministic `transferContent = "ELLORA GOI" + id`, `paymentReportedAt`, `paymentReference`, `paymentConfirmedAt`, and `receivedAmount`. Store `paymentConfirmedBy` internally for audit, but do not expose the admin UUID in owner/admin Request DTOs, consistently with the existing reviewer privacy. No payment instruction/audit field is public salon/catalog data.
- Extend `Plan` with `registrationAvailable:boolean = enabled && monthlyPrice>0 && sharedQrConfigured`. Keep `enabled` as the raw admin setting. Public/owner UI uses `registrationAvailable` for availability; admin retains its raw enabled checkbox and sees the readiness status. This prevents legacy enabled-zero or missing-QR configurations from being advertised as purchasable without changing their stored prices/settings.
- Unique transfer content derives from the immutable request ID (no extra content column needed), is distinct from percentage-fee bill content, and is shown alongside the exact immutable `quotedPrice` and QR. Tell owners to set/check amount and content manually; a static uploaded QR does not automatically encode the request amount/content. A future QR upload cannot replace a request's saved destination.
- Add `POST /api/owner/subscription/requests/{id}/payment` with `{reference?:string}` (trimmed, max 100). Require the caller's own salon, PENDING request, positive quote and prepared QR; set server `paymentReportedAt` and the first reference only. Return the request. Replay while still PENDING is idempotent and preserves the original declaration. This endpoint never changes salon tier/dates, confirms money or accepts client timestamps/amount/status. Non-owner is 403; a terminal request is not reportable.
- Root's read-only check confirmed an existing configured QR and one user-created subscription request. For legacy PENDING requests, add owner-only `POST /api/owner/subscription/requests/{id}/prepare-payment` (empty body). Resolve ownership, lock salon then request, require a positive pending quote, and copy the current QR only if the request snapshot is absent; return instructions. Never overwrite a saved snapshot or mark payment reported/received. Current catalog disabling/repricing does not prevent preparing/reporting the previously accepted quote. If QR is missing, return a clear configure-QR error. This self-service path avoids instruction or business-state backfills and works after later bank configuration; no bank-details question is needed.
- Extend existing admin decision `PATCH /api/admin/subscription-requests/{id}` to `{status:'APPROVED'|'REJECTED',note?,paymentReceived?:boolean,expectedAmount?:number}`. APPROVED requires all of: PENDING with a positive quote, prepared QR, owner payment report present, `paymentReceived === true`, and `expectedAmount.compareTo(quotedPrice) === 0`. Never default the boolean/amount. Reject remains possible before/after a report, requires its existing reason and does not change salon entitlement.
- Successful approval stores confirmed amount/time/admin UUID, then grants the existing one-month period from decision time or active same-tier expiry, in the same transaction. Preserve existing grant-window history and same/opposite terminal replay rules. A same-result replay must not extend dates or fabricate payment audit for an old approval. Existing approved periods remain effective and are not retroactively marked bank-paid.
- Use existing validation/error/envelope conventions. Reference/note/expectedAmount are server validated; positive whole-VND constraints apply to approval amount as well. No proof file upload or public lookup by transfer content is added.

## Persistence, locks and compatibility
- Add nullable request columns `payment_qr_url` (TEXT), `payment_reported_at` (TIMESTAMP), `payment_reference` (VARCHAR(100)), `payment_confirmed_at` (TIMESTAMP), `payment_confirmed_by` (UUID), `received_amount` (NUMERIC(15,0)). Vietnam local timestamp conventions remain unchanged. Legacy rows stay null, with no invented reports/receipts or active-period rewrite.
- Add an idempotent additive `subscription-bank-transfer.sql` and manual-only rollback. Add only nullable columns/checks: no instruction, price, report, receipt, review or period backfill. Check confirmation fields are all-null or all-present with positive amount equal to quote, positive quote and reportedAt present; confirmed audit requires APPROVED. Permit legacy approved rows with all confirmation fields null. Keep existing pending/final-state constraints, uniqueness, RLS and request history intact.
- Every owner/admin request mutation resolves salon ID without preloading stale entities, then locks **Salon → request**. Creation locks **Salon → catalog**, then copies the current settings QR; legacy preparation locks **Salon → request** and fills a missing snapshot only. Reading a QR string needs no additional settings write lock; the immutable request snapshot is what the owner subsequently sees. Existing QR updates remain unchanged. Approval does not consult/change current QR/catalog prices. Locking and database checks must prevent double activation under concurrent reports/decisions.
- Admin plan enabling validates positive price; missing QR makes `registrationAvailable=false`, with a clear link to existing `/admin/billing` QR configuration. New request creation independently rechecks enabled/positive price and QR. Existing enabled zero-price rows are treated unavailable without rewriting prices; owner/admin surfaces explain the new requirement. No public banking/contact details are introduced.
