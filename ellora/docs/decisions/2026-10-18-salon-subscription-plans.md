# Monthly salon subscription plans

> Payment correction: the user's later transfer-first requirement is defined in `2026-10-18-subscription-bank-transfer.md`. It supersedes the approval-without-payment and enabled-zero-price assumptions below; existing badges, ranking and month-period rules remain unchanged.

## Scope and decisions
- The user requested two monthly salon plans: `STANDARD` (Thường, badge **Shop yêu thích**) and `VIP` (VIP, badge **Shop đối tác**). Admin sets the actual prices; owners submit requests and admin explicitly approves before activation. The user authorized Codex to substitute for the unavailable Hermes workflow. This architect plan precedes implementation.
- Read AGENTS, product spec, AI context/conventions/workflows, architect prompt, stack/frontend/backend/API/workflow guidelines, current Salon, platform-fee billing, public search repository and ForBusiness flow. Reuse Angular reactive forms/signals, Spring/JPA/PostgreSQL and existing role/layout patterns. No new dependency, gateway, automatic charge/renewal, email job or percentage-billing change. Existing booking/features remain available without a plan.
- Price is VND per **one calendar month**. No invented amount or free trial: both catalog rows initially have `monthlyPrice=null, enabled=false`. Admin may configure a whole-VND price **>=0**, including an explicit promotion price of zero. Remove the existing unsupported ForBusiness free-month promise.
- Catalog changes affect new requests only. A pending request keeps its accepted quoted price, and an already active period keeps its entitlement even if the catalog is disabled/repriced. Approval is the admin's manual authorization to activate that quoted request; this feature does not assert a verified bank transaction.

## API contract
All paths below include the normal `/api` prefix and use existing `ApiResponse`/`PageResponse`; paged lists default `page=0,size=20`, clamp size to 1..50 and reject offsets exceeding integer range. Tier/labels are fixed code values.

| Method and path | Request / response |
| --- | --- |
| `GET /salon-plans` | Public catalog of exactly two rows, STANDARD then VIP, including unavailable rows. `Plan={tier,displayName,badgeLabel,monthlyPrice,currency:'VND',enabled,termMonths:1}`. |
| `GET /owner/subscription` | Owner's salon only: `{salonId,effectiveTier,badgeLabel,startsAt,expiresAt,pendingRequest}`. Effective tier/badge are nullable; dates describe the last approved period even after expiry. |
| `GET /owner/subscription/requests?page&size` | Owner's paged request history, newest id first. |
| `POST /owner/subscription/requests` | `{tier:'STANDARD'|'VIP',expectedPrice:number}`; validates current enabled catalog and exact current price, creates and returns one `PENDING` request. No client salon ID, dates or status accepted. |
| `GET /admin/subscription-plans` | Full two-row catalog, admin only. |
| `PUT /admin/subscription-plans/{tier}` | `{monthlyPrice:number|null,enabled:boolean}`. When enabled a price is mandatory; nullable price permitted only while disabled. Returns the updated plan. |
| `GET /admin/subscription-requests?status=PENDING&page&size` | Admin paged queue/history, newest id first. Status optional, absent means all; explicit PENDING/APPROVED/REJECTED only. |
| `PATCH /admin/subscription-requests/{id}` | `{status:'APPROVED'|'REJECTED',note?:string}`. Returns request after locked decision; reject requires a nonblank reason. |

- `SubscriptionRequest={id,salonId,salonName,tier,quotedPrice,status,createdAt,reviewedAt,reviewNote,startsAt,expiresAt}`; pending/rejected period fields are null. Store reviewer UUID for audit server-side; do not expose private user/contact data in public catalog or salon results.
- Monetary inputs: required where specified, finite nonnegative whole amounts fitting `NUMERIC(15,0)` (`@DecimalMin("0"), @Digits(integer=15,fraction=0)`); price comparisons use `BigDecimal.compareTo`, not client arithmetic. Notes maximum 1000 characters. Unknown tier/status or null decision/enabled is 400. Stale price, unavailable plan, duplicate pending, non-ACTIVE salon or active conflicting tier is a meaningful 400 using existing exception conventions. Auth/ownership remains 401/403 and unknown IDs 404.
- Public summary/detail add **effective only** `subscriptionTier:'STANDARD'|'VIP'|null` and `subscriptionBadge:string|null`; never expose pending proposals, prices, requester/reviewer or raw expired tier.

## Schema and state rules
- Add `salon_subscription_plans`: `tier VARCHAR(16)` PK restricted to STANDARD/VIP; nullable `monthly_price NUMERIC(15,0)`, `enabled BOOLEAN NOT NULL DEFAULT false`, `updated_at TIMESTAMP`, `updated_by UUID` nullable for initial seed. Check nonnegative price and price present when enabled. Seed both disabled rows idempotently with no price; startup must not silently invent/enable plans.
- Add three nullable columns on `salons`: `subscription_tier VARCHAR(16)`, `subscription_starts_at TIMESTAMP`, `subscription_expires_at TIMESTAMP`. Tier nullable or STANDARD/VIP; a populated period requires all three and expiry > start. Null legacy data means no plan.
- Add `salon_subscription_requests`: identity id, salon FK, tier, non-null `quoted_price NUMERIC(15,0)`, status, created_at, reviewed_at, review_note, reviewed_by UUID, starts_at/expires_at. Keep history immutable except the single PENDING-to-final decision. Add partial unique index on salon_id WHERE status='PENDING', and useful `(status,id)` / `(salon_id,id)` indexes. Enable RLS on both new tables consistently with existing backend-only Supabase access.
- Supply an additive, idempotent `src/main/resources/db/salon-subscriptions.sql` for Supabase `ddl-auto:none`; schema application is a separate explicit operational action. No diagnostic business writes. Existing fields, percentage fee policies/statements, outbox and booking SQL remain untouched.
- Use injectable `Clock`, `Asia/Ho_Chi_Minh` and `LocalDateTime` consistently with existing local database timestamps. Effective period is `startsAt <= now < expiresAt`; malformed/missing/future/expired periods or non-ACTIVE salons have no public badge/rank. Expiry is computed on read, with no cron/update requirement.
- Only ACTIVE salons may request/receive approval. Lock salon for all request/decision mutations. During creation, also lock the catalog row, compare `expectedPrice`, reject an existing pending request and active different tier, then save the quote. Database uniqueness backs up the salon lock. Catalog updates lock only the catalog row.
- Approval first resolves salon ID, locks salon, then locks/reloads request and revalidates ownership/status/salon/tier conflict. Do not lock request then salon. No catalog lock or repricing at approval: approve the stored quote, even after catalog changes. Reject does not change salon entitlement. Two concurrent approvals cannot activate twice.
- Same-tier renewal while active preserves the salon's original start and extends **current expiry** by `plusMonths(1)`; the request's granted-month snapshot is `[oldExpiry,newExpiry)`. New/expired activation starts at decision `now`, ends `now.plusMonths(1)`, and that window is also the request snapshot. Active tier changes are blocked at request and approval until expiry; UI explains this. Repeating the same terminal decision returns the existing result with no date extension; an opposite terminal decision fails. Do not overwrite prior notes/reviewer on a replay.

Public detail also computes badge with the same entitlement rule. Frontend must not resort only a page. Labels disclose that subscribed salons are prioritized, including when sorting by rating/distance; distance still describes the true center.

Render badges consistently on existing salon card variants, detail and manually rendered nearby cards, without covering booking/map controls. Keep semantic headings, keyboard labels, errors/loading/empty states, existing rose styling, mobile responsiveness and SSR guards.
